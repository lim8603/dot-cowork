# 도구/환경 운영 가이드 (Tooling Environment Guide)

> 도구별 실행 제약, 진입점 동기화, 네트워크 의존 운영을 분리해 관리하는 가이드

---

## 목적

- `session_protocol.md`는 세션 공통 흐름과 불변 규칙만 유지한다.
- 이 문서는 자동승인, 진입점 동기화, 업그레이드처럼 **도구/환경에 따라 달라질 수 있는 운영 지시**를 다룬다.
- 도구별 시작 예시는 `.cowork/README.md`에 두고, 진입점에는 작업 판단에 필요한 최소 지시만 둔다.

## 1. 도구별 승인과 실행 제약

- 자동승인은 필수 전제가 아니다. 지원하지 않거나 Human이 원치 않으면 수동 승인 흐름으로 계속 진행한다.
- 세션 시작 시 도구 제약 때문에 막히더라도 공통 프로토콜은 유지한다. 확인이 필요한 것은 승인 방식, 파일/쉘 실행 가능 여부, 네트워크 접근 가능 여부, 장기 실행 제약이다.
- 도구별 설정 예시가 필요하면 `.cowork/README.md`에서 해당 도구 항목을 사용한다. 한 도구의 명령이나 UI 옵션을 공통 프로토콜에 복사하지 않는다.
- 자동승인이나 유사 설정을 권장하더라도, Human 확인은 1회만 요청하고 거절되면 반복하지 않는다.

## 2. 진입점 동기화 규칙

진입점에는 안정적인 프로젝트 식별·문서 경로·공통 실행 경계만 둔다. Phase, 활성 Task, 다음 Milestone, 배포 버전은 `project_state.md`에서 읽으며 진입점에 복제하지 않는다. 실제 기술 스택은 `tech_stack.md`를 기준으로 한다. 재개 시 진입점 요약이 기준 문서와 충돌하면 근거를 확인해 오래된 요약을 링크로 교체한다.


- 4대 진입점 파일은 같은 `.cowork/` 공유 기준 문서를 각 도구에 맞게 노출하는 짧은 안내문이다. 현재 상태와 기술 스택의 값은 복제하지 않는다.
- 아래 항목이 바뀌면 4대 진입점 전체를 함께 검토한다.
  - 프로젝트명, 핵심 문서, 주 언어/문서 언어 정책
  - Phase 표현 방식, 브리핑 흐름, 요청 의도별 실행 규칙
  - 기술 스택 기준 문서 경로, 핵심 워크플로우, 업그레이드/릴리즈 안내
  - 다른 도구와 공유해야 하는 자동화 문구
- 도구 전용 시작 예시는 `.cowork/README.md`에서 관리한다. 공통 계약이 바뀌면 4대 진입점을 동기화한다.
- 진입점 변경이 발생하면 기록이 필요한 작업의 세션 로그 또는 릴리즈 기록에 변경 이유를 남긴다.

## 3. 프레임워크 업그레이드 운영

### 트리거

- Human이 프레임워크 업그레이드를 요청한다. 단어 언급만으로 실행하지 않는다.

### 기준 문서

- 실행 경로와 환경별 분기: `01_cowork_protocol/tooling_environment_guide.md`
- 현재 설치 버전과 대상 버전 판정, 파일 분류: `.cowork/upgrade_manifest.md`

### 공통 운영 규칙

1. 먼저 현재 프로젝트의 `.cowork/upgrade_manifest.md`에서 설치된 `Version`을 읽는다.
2. 네트워크 접근이 가능하면 GitHub API로 최신 릴리즈를 조회한다.
   - `GET https://api.github.com/repos/lim8603/cowork-context-framework/releases/latest`
3. 네트워크 접근이 불가하면 `.cowork/.upgrade/archives/v{버전}/`에 수동 배치한 zip을 사용한다.
4. 대상 릴리즈의 `upgrade_manifest.md`를 읽고 `Version`과 `From`을 확인한 뒤, 항상 `From` 체인으로 인접/건너뛰기 업그레이드를 판정한다.
5. 건너뛰기 업그레이드는 최신 버전 직행 적용보다 **중간 버전 순차 적용**을 우선한다.
6. 적용 전에 `.cowork/.upgrade/upgrade_plan_v{from}_to_v{to}.md`를 만들고, 검증된 순서와 해제 경로를 기록한다.
7. 각 단계는 매니페스트의 `ADD / REPLACE / MERGE / SKIP` 분류대로 적용한다.
8. `MERGE`가 필요하거나 판단이 어려운 경우는 Human 승인 후 적용한다.
9. 프로젝트가 채운 데이터는 보존하고, 프레임워크 구조와 규칙만 갱신한다.
10. 업그레이드 전에는 git commit을 권장하고, 계획 파일과 결과 로그는 검증이 끝날 때까지 `.cowork/.upgrade/`에 유지한다.

## 4. 유지 보수 체크

- 도구별 설정 예시가 바뀌면: 해당 진입점 문서만 먼저 갱신한다.
- 공통 운영 경계가 바뀌면: `session_protocol.md`, 이 문서, `document_role_inventory.md`, `document_change_impact_matrix.md`, 필요 시 `upgrade_manifest.md`를 함께 본다.
- 경로/파일 구조가 바뀌면: 4대 진입점과 `upgrade_manifest.md`까지 포함해 동기화한다.

## 5. 세션 규율 강제 (Enforcement Hooks) — F-10

> `session_protocol.md`의 세션 시작 체크·자동 기록 규칙은 대부분 **AI의 자발적 준수**에 의존한다(모델·컨텍스트에 따라 조용히 깨질 수 있다). 되돌리기 어려운 규율은 도구의 **훅(hook)** 으로 기계적 강제를 걸 수 있다.

### 강제 가능한 체크 (예)

| 체크 | 근거 규칙 | 강제 아이디어 |
|------|-----------|---------------|
| 작업 로그 생성 여부 | `session_protocol.md` §자동 기록 1 | 기록이 필요한 작업일 때만 로그 존재를 확인. 읽기 전용 요청은 제외 |
| 라이브 상태 문서 크기 예산 | F-05 | 훅이 `project_state.md`+`my_state.md` 크기를 측정, 예산 초과 시 R1/R2 하베스트 권고 표시 |
| 이월 항목 확인 | F-02 | 작업 미지정 브리핑에는 이월을 포함하고, 특정 작업에서는 관련 항목만 확인 |
| openapi/스키마 드리프트 | 프로젝트별 | 커밋 전 훅이 재생성 diff=0 확인(계약 있는 프로젝트) |
| 커밋 메시지 컨벤션 | decision matrix | commit-msg 훅으로 접두사 검증 |

### 운영 원칙

- **강제 수단은 도구·환경에 따라 다르다.** 구체 구현(에이전트 훅, git 훅, CI 잡)은 현재 도구의 진입점 문서(`CLAUDE.md` 등)와 저장소 설정에 둔다. 이 문서는 "무엇을 강제할 수 있는가"의 목록과 배치 원칙만 정의한다.
- 예시(도구 비종속): git `pre-commit`/`commit-msg` 훅, CI 잡, 에이전트 세션 시작/종료 훅.
- 훅은 **차단이 아니라 기본 권고**로 시작한다(fail-closed가 필요한 항목만 차단). 오탐이 세션을 막으면 규율이 우회된다.
- 강제 항목을 추가/변경하면 세션 로그와, 도구 공통 계약이 바뀐 경우 4대 진입점을 함께 갱신한다.
